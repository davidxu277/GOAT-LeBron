## 二、重点讲一个例子：噪声带不是量一次就永远有效的（对应 #7）

这是最容易被忽略、也最容易悄悄搞错分数的一件事，**训练/可靠性这块工作的人
（跑真数据、调数据规模的人）必须记住**。

### 是什么

"噪声带"就是：同一份配置、同一套代码，只换一个随机数种子，重新训练一次，
分数会自己抖多少。这个抖动幅度决定了"这次分数变化算不算真的进步"——
变化幅度比抖动还小，那就是运气，不是本事。

### 关键事实：数据量越大，抖动越小

这份数据集有个特点：点击这个行为的例子很多（几十万条），但购买这个行为的
例子极少（现在小份数据上验证集只有 38 条转化）。例子越少，测出来的分数
自己抖起来的幅度就越大——这是统计学的基本规律，不是这份数据独有的毛病。

我们实测过（`agent.cli noise --seeds 3 --fidelity 小份`）：

| 数据规模 | 点击AUC 抖动 | 购买AUC 抖动 |
|---|---|---|
| 小份（现在测的） | ≈ 0.001 | ≈ 0.09（38 个转化样本） |
| 中份 / 大份 / 全量 | 没测过，但转化样本会更多，**理论上会更小** |

### 这会怎么坑到你

系统跑的时候会自动"升档"：数据量不够看出差别了，就自动换更大的数据规模
接着跑（`agent/loop.py` 里的 `escalate` 函数）。**但升档只是换个数据量重新
训一次，不会重新测噪声带**——整场用的噪声带门槛，从头到尾都是开跑前那一次
测出来的数字。

具体后果：如果你拿"小份"测出来的噪声带（购买 AUC ≈0.09）去卡"全量"数据
跑出来的结果，而全量数据上真实的抖动可能只有 ≈0.02——那系统会用一把
过松的尺子去判断"这次改动算不算真进步"，本来一个 0.03 的真实提升，
理论上该被判定为"确实变好了"，却因为门槛设得太宽被当成"这点变化不算数"。
反过来，拿"全量"测出来的窄门槛去卡"小份"的结果，又会把小份数据上正常的
抖动误判成"真的有效"。

### 你该做什么

**换数据规模（尤其是切到中份/大份/全量）之前，先重新测一次噪声带：**

```bash
python -m agent.cli noise --seeds 3 --fidelity <对应的档位> \
    --train <这个规模的训练集> --val-features <这个规模的验证集>
```

这条命令会覆盖写入 `logs/noise_bands.json`。之后启动的 `run --rounds N`
会自动读这份最新的文件（`agent/cli.py: _noise_bands()`），不用改代码，
但**你必须记得在换数据规模之后手动跑一次这条命令**，系统不会替你自动跑。

如果你要做的是"跑一场会自动升档很多次"的长会话，现在的代码结构决定了
没有一个完美答案——要么接受"全程用起步档位的噪声带"这个已知的不精确
（现在的行为），要么手动分段跑（每次升档前先手动测一次噪声带、重启一场）。
**这是我目前没有改的地方，留给你判断要不要改、怎么改**（涉及要不要在
`escalate()` 里插一次自动重测，会增加时间和 token 成本，需要衡量值不值）。

## 三、需要你做决定的事（我诊断出问题，但改法不止一种，需要你拍板）

### 军师不知道执行器现在只能跑哪些方案

方法库有 26 张卡，但训练代码目前只支持"加特征"这一类改动，外加早停、
负采样——一共 5 张卡真能跑。军师完全不知道这条边界，可能会推荐一个
根本跑不了的方案（比如"用 ESMM"），工兵写完代码、训练直接拒绝，
一整轮的大模型调用全部浪费（今晚实测过一次真实场景：一次这样的轮次
烧了 44930 个 token，跑了 334 秒训练，最后什么结果都没有）。

三种改法，各有取舍：

1. **在筛卡片那一步（纯代码）直接把跑不了的卡过滤掉。**
   最省钱，但军师永远看不到那些卡，也就没法在推理里提"我知道这个更好，
   但现在做不到"——创新性的推理链条会显得不完整。
2. **在军师的说明书里明确写清楚边界**，让它自己避开。
   更诚实，保留了"知道有更好的方法但受限于工具"这层推理，但依赖模型
   听话，不是硬保证。
3. **两者结合**：说明书里讲清楚边界（给推理留空间），筛卡片那一步只是
   降低这些卡的优先级而不是完全隐藏（比如打个"目前跑不了"的标签一起
   喂给军师，让它自己决定要不要在方案里提一句"这个更合适，但受限于
   当前工具选了退而求其次的方案"）。

我倾向第 3 种，但这个直接影响"创新性"这项怎么被评委看到，建议你们
（尤其是负责这部分叙事的人）一起定，我不替你们做这个决定。

### predict 导出的时候没有做"能力检查"

评分那条路上有一道关卡（`harness/executor.py: check_supported`），
配置要的东西做不到就当场拒绝。但导出预测那条路（`predict_frame`）
没接这道关卡——如果拿一个写着"用 deepfm"之类做不到的配置去导出预测，
它不会报错，而是**悄悄训一个普通 LightGBM，然后给你一份看起来正常的
预测文件**，没有任何提示这份预测其实没有按配置跑。

这个我认为没有争议，就是该修（把 `check_supported` 也接到 `_fit_predict`
里），只是还没来得及做，留在这里免得忘。
